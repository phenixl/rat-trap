# 从屏幕捕获中恢复光标的颜色与 alpha

本文是 `src/RatTrap/Reconstruct/` 背后的推导过程。它记录了这套方法是什么、每个选择为何如此做出、哪两种方案被弃用以及它们为何不合格，以及——这一点很重要——哪些内容可证明是不可恢复的。

---

## 1. 问题

应用程序会把自绘光标画进自己的帧里。因此，在屏幕所显示的内容中该光标就是普通像素，而操作系统里没有任何东西会把它交出来：`GetCursorInfo` 报告的是*系统*光标，而桌面复制（Desktop Duplication）与 GDI `BitBlt` 得到的桌面图像都**不包含**系统光标（已实测；见 `measured-behaviour.zh-CN.md`）。所以唯一的来源是合成结果，而把光标与它背后的场景分离出来的唯一办法，就是观察二者如何各自独立地变化。

## 2. 模型

设 `s` 为屏幕像素，`t` 为时间，`h_t` 为指针热点（hotspot），`r = s - h_t` 为*光标局部偏移*。给光标一个固定的 alpha `alpha(r)` 和颜色 `C(r)`——之所以固定，正是因为假设光标不改变形状：

```
covered:    D_t(s) = alpha(r) * C(r) + (1 - alpha(r)) * B_t(s)
uncovered:  D_t(s) = B_t(s)
```

`B` 是光标背后的内容，未知。所有运算都直接在捕获到的 8 位 sRGB 编码值上进行，**不**做线性化，因为合成器（compositor）执行混合所处的正是这个域；先做线性化会建模成一种与产生这些像素的实际操作不同的操作。

## 3. 信息从哪里来

有两种机制提供了让该方程组可解的变差，求解器两者都用：

**空间维度。** 每当指针移动，同一个偏移 `r` 就会落在不同的屏幕像素上，因为 `s = h_t + r`。每一次落点都给出一对 `(B(s), D(s))`，而其中的 `B` 是*不同的*。因此，只要把指针在带纹理的背景上移动一次，每个偏移就已经能获得许多对样本，而场景本身完全没有任何变化。这正是该工具在完全静止的屏幕上也能工作的原因。

**时间维度。** 固定的屏幕位置也会看到其背景随时间变化——动画、滚动、视频——即使指针停着不动，这也会增加样本对。

实际结果就是该工具打印出的使用说明：*把指针在带纹理的区域上移动*。除此之外什么都不需要。

## 4. 求解

对每个偏移 `r`，观测值是三个通道上的 `(B_i, D_i)`。把逐通道模型写成

```
D_c = m * B_c + k_c        with  m = 1 - alpha  and  k_c = alpha * C_c
```

### 4.1 一个斜率，而不是三个

`alpha` 是像素的属性而非通道的属性，所以 `m` 在三个通道之间是**共享**的，而 `k_c` 是逐通道的。这一点很重要：若独立拟合每个通道，各通道就会对 `alpha` 给出不一致的结果，而这种不一致会在抗锯齿边缘上表现为彩色镶边（colour fringing）——恰恰是在 alpha 变化最快、约束最弱的地方。

### 4.2 为什么它是闭式解

对固定的 `m`，最小二乘意义下的 `k_c` 为 `mean(D_c) - m * mean(B_c)`。把它代入后，就只剩一个关于单一未知量 `m` 的二次式，其最小值在下列位置取得

```
        sum_c Cov(B_c, D_c)
m*  =  ---------------------
          sum_c Var(B_c)
```

因此累加器只存储求和量——每个通道的 `sum B`、`sum D`、`sum B²`、`sum D²`、`sum BD`——而从不保存样本列表。没有迭代，不需要初值猜测，也不存在会失败的收敛过程。于是

```
alpha = 1 - m*          C_c = k_c / alpha        (for alpha away from 0 and 1)
```

而拟合的残差 RMS 同样有闭式解，每个像素所报告的置信度值正是由它推导出来的。

## 5. 估计背景

求解过程需要每次观测时刻的 `B`，而两种被弃用的设计恰恰都败在背景模型上。

### 5.1 已弃用：带门限的 IIR 滤波器

当一个样本与当前估计足够接近时，就把它并入该估计；否则拒绝。这样做开销很低，每像素 O(1)，而且*看起来*是对的——光标只在部分时间覆盖任意给定像素，所以估计应当收敛到背景上。

但它失败得很惨。设想某个像素的**第一次**观测恰好就是被光标覆盖。不透明光标无论背后是什么都会产生相同的值，所以*下一次*观测也与之匹配，该估计被判定为已确认，于是滤波器就自信地把**光标当成了背景**。此后该像素上每一个真正的背景样本都会被拿来与它配对——关系被反转——而最小二乘会悄悄地对这个反转关系拟合出一条斜率。

一旦把模型图打印出来，症状就再明显不过：恢复出的热点落在偏移 33 而不是 3，因为每个偏移都有一条幽灵样本对被记录在*整个*区域上，而不是只在字形上。

### 5.2 已弃用：用样本数量确认估计

要求估计必须再经一次观测确认（`age >= 2`）能排除首帧的情形，却排除不了普遍情形：一个连续两次被覆盖的像素会在其估计仍然是光标时就达到 `age >= 2`。

### 5.3 采用：有界窗口的中位数

对每个屏幕像素，保留最近 `N`（默认 15）次观测并取逐通道中位数。光标只占据它所经过区域的一小部分，因此对任意给定屏幕像素，近期样本中的大多数都是真正的背景，而中位数会挑中它们——**无论哪个样本先到**。它也能自行适应永久性的局部变化，因为陈旧样本会自然老化淘汰，而且它没有需要调参的学习率。

只有当窗口中的**严格多数**与估计一致时，该估计才被判定为可用（`MinBackgroundInlierFraction = 0.55`）。这个阈值并非随意设定：它恰好就是“中位数即背景”这一陈述成立的条件。更低的阈值会放行诸如含 8 个光标样本和 7 个背景样本的窗口——这种窗口的中位数*就是*光标——于是 §5.1 的失败重演一遍；在 0.40 的阈值下这一失败仍可实测到，它在一个合成测试十字旁边产生了一片虚假的棋盘状幽灵像素。

### 5.4 最低覆盖证据

只有当某个光标局部偏移至少拥有 `MinCoverageEvidence = 3` 对样本时，才把它当作光标的一部分。单独一对样本可能来自一个曾短暂错误的背景估计，它并不是被覆盖的证据。没有这个下限时，这样一对样本就会把恢复出的包围盒扩大二十个像素，并连带移动热点，于是输出就不只是有噪声，而是**位置错误**。

### 5.5 覆盖率，它是把字形与噪声区分开的东西

只有当某个偏移在被观测到的次数中，至少有 `MinCoverageRate = 0.25` 的比例表现为被覆盖时，它才算作光标的一部分：

```
pairs / (pairs + uncovered)  >=  0.25
```

真正的光标在指针每次把某个偏移放到屏幕上时都**会**覆盖它，因此其覆盖率接近 1——在合成 XOR 用例中实测为 99.8%。而来自曾短暂错误的背景模型的残留，不过是几百次普通观测中的寥寥几对样本——实测为 0.2%。

这道防护的存在源于一次真实的失败，而所有基于形状的替代方案都没能抓住它。在一块普通桌面上（**根本没有任何东西绘制光标**，因为桌面复制会排除系统光标）运行重建，结果在 160×162 的方框内散落着 402 个“被覆盖”像素，原因是一个文本正在滚动的终端会周期性地与自己的背景估计不一致。更早的版本把这一结果当作光标报告出来，连热点都齐全，还写进了磁盘。一个看起来合理的错误答案比一次失败更糟，因为它与正确答案无法区分。

所有形状检验都被否决了，值得记录下原因，因为每一条在真正尝试之前都显得合理：

| 检验 | 为何是错的 |
| --- | --- |
| “字形必须是紧凑的——被覆盖像素必须填满其包围盒中相当大的一部分” | 十字准星是稀疏的。一个 32×32 的十字准星在 1024 像素的方框里只覆盖 63 个像素：6%。 |
| “字形必须是连通的” | 移动/调整大小光标是四个互不连通的箭头。 |
| “热点本身必须被绘制出来” | 移动光标的热点位于中心处的空隙中；有些十字准星也有空隙。 |

以上每一条都会否决一个合法而常见的光标。信息是否可得则没有这类盲点，这正是这些防护都围绕信息来设计的原因：上文的覆盖率，以及 §7 中当两种机制都无法学到任何东西时的拒绝输出。



### 6.1 完全不透明的像素不需要背景变化

若 `alpha = 1`，则对任何背景都有 `D = C`，因此合成结果是常量。拟合会得到 `m = 0`，alpha 在完全不借助背景变化的情况下就得出 1——这就是为什么即使下方的背景从未变化，实心光标的内部也能被精确恢复。已验证：一个合成的完全不透明光标恢复后**颜色误差为 0 个色阶**。

### 6.2 XOR 合成的光标是另一种模型

传统光标和掩码彩色（masked-colour）光标根本不进行混合：`screen = background XOR mask`，其中掩码为常量。该关系对背景不是仿射的，所以 alpha 模型对它拟合得很差，恢复出的“alpha”也没有意义。因此累加器还携带第二种假设——每一对样本的 XOR 差值——当某个像素至少 95% 的样本对在同一个差值上一致*且*背景发生过变化时，就把它归类为 XOR 合成。已验证：一个合成的 XOR 十字能逐位精确地恢复其掩码（`FF,7F,00`），并以准确的 XOR 掩码写出，从而重现原始渲染结果。

### 6.3 alpha 恰好为 0 或 1

当 `alpha >= 0.98` 时，除法 `k / alpha` 会放大噪声，因此改用合成值的均值——这是正确的，因为不透明像素的合成值*就是*它的颜色。当 `alpha < 0.02` 时，合成值跟随背景，于是该像素被判定为透明，而不是送去除以一个接近零的数。

## 6. 特殊情况，以及它们为何不是优化

## 7. 可证明不可恢复的内容

如果一个像素在整个观测期间都被覆盖，**并且**它下方的背景从未变化，那么观测值就是一个常量，等于 `alpha*C + (1-alpha)*B`，而两个未知量都是自由的。对同一配置再做多少次观测都无法解出它。求解器会把这些像素报告出来，而不是编造数值，CLI 会打印出它们有多少个以及该如何处理。

有两种配置会让这一点显现出来，两者都由自检覆盖，而这些自检断言的是**失败报告**，而不是某个神奇的结果：

| 配置 | 预期行为 |
| --- | --- |
| 静止背景上的静止光标 | “没有记录到任何样本对，因此无法求解”，并指向合成器路径，该路径不需要重建 |
| 指针在完全均匀的背景上移动 | 样本对存在，但背景方差为零，因此 alpha 不可辨识；受影响的像素会被计数，并告知用户移动到纹理更丰富的区域 |

即使在均匀背景的情形下，完全不透明的像素仍能被精确恢复（§6.1），因为它们从不需要背景。只有部分透明的像素会丢失。

## 8. 组装输出

* 输出范围是所有具备足够覆盖证据的偏移的包围盒，再外扩一个像素的边距，用于容纳那些始终只产生弱样本的抗锯齿边缘。
* 热点由几何关系定义，而不是靠猜：偏移 `(0,0)` *就是*指针位置，因此输出图像中的热点为 `(-minRx, -minRy)`。
* 完全透明像素之下的 RGB 通过一次短程膨胀（dilation）由最近的不透明邻居填充。这些字节在查看器中不可见，但会被双线性过滤读取，此时透明边缘下方的黑色会变成一圈暗色光晕。
* 如果 XOR 分类的像素在被覆盖像素中占绝大多数，光标就以精确的 XOR 掩码写出（`CursorEncoding.XorMasked32`）；否则以 alpha 混合方式写出。

## 9. 已知限制

* **配准（registration）。** 求解假设某一帧所报告的指针位置就是该帧像素的真实热点。一个像素的误差就会把 alpha 抹到相邻偏移上。当热点来自 `GetCursorPos` 时这是精确的；未来若改用运动跟踪的指针来源，就需要增加一次配准细化过程（见 `ROADMAP.zh-CN.md`）。
* **形状变化。** 会动或会改变形状的光标违反了固定 `C(r)`、固定 `alpha(r)` 的前提，产生的结果是其若干形状的混合。检测这一点并按时相切分（phase-segment）是 `ROADMAP.zh-CN.md` 的主题。
* **指针停驻时的背景运动。** 这里只利用了空间机制。从帧内其他地方预测静止光标下方的背景属于运动估计问题，尚未实现。
* **XOR 与 alpha 的混合。** XOR 检验与仿射拟合（affine fit）在逐像素上是互斥的。同时使用两者的光标会按区域分类，而整个文件的 XOR 编码只有在 XOR 占主导时才会被选用。

## 10. 十字准星模式：固定覆盖层需要不同的背景

以上所有内容都假设光标在移动，正是这一点才让逐像素的时间中位数能够找到背景。十字准星（crosshair）是从结构上、而非偶然地违反这一假设：它停在一个固定的屏幕位置上，而场景在它背后运动。它所覆盖的每一个像素在*每一*帧中都被覆盖，于是时间窗口里填满的全是合成值，而该窗口的中位数**就是**合成值。背景模型恰恰采纳了它本该看穿的那个东西——§5.1 的失败以另一条路径再次出现，而且再怎么增加观测也修不好。

替代方案是第二个背景来源，由 `BackgroundSource.SpatialNeighbourMedian` 选择：**在同一帧内**，取该像素八个邻居在两个半径上的中位数。它能奏效是因为十字准星很细。从它笔画上任意一点往外几个像素就是普通场景，而从笔画上大多数点出发，大多数方向都能离开它——对于水平臂上的一个像素，沿臂方向的两个样本仍落在它上面，而另外六个不会。取两个半径而不是一个，是为了让宽度出乎意料的笔画仍然有大多数样本落在它之外。

只有当场景在该尺度上是平滑的时，该样本才是有效的替代值。误差是场景在采样环上的曲率项 `d^2 * f'' / 2`，这正是合成测试使用平缓渐变而非白噪声的原因：在 9 像素半径下，一个特征尺度约 150 像素的场景只贡献几个色阶的误差，而像素级噪声则会贡献其全部幅度。

已用真值（ground truth）验证：在会变化的场景上，一个合成十字准星恢复出的笔画 alpha **精确**、笔画颜色**精确**，边缘 alpha 的平均误差为 0.004，并且在 16 019 个背景像素上**误报为 0**。在不变的场景上，alpha 确实不可辨识——但对不透明部分答案仍然正确，因为不透明像素的合成值不取决于它背后是什么——所以该工具会给出答案并说明哪些部分属于假设，而不是拒绝输出。

有两点值得说明：

* **拒绝规则因模式而异。** 在时间模式下，“指针从未移动、也没有解出任何东西”属于拒绝输出，因为此时观测中没有任何东西携带信息。在空间模式下这一检验无法适用，因为该几何按设计就不移动；覆盖改由与周围场景存在一致差异这一直接证据来支撑。
* **场景变化检测在空间模式下被禁用。** 它的存在是为了让某个时间模型失效——当该模型的历史所描述的内容已不在屏幕上时。在空间模式下没有可失效的历史，而且繁忙的场景会不断触发该检测器——恰恰在场景给求解器提供最多可用信息的时候压制样本对的记录。

## 11. 十字准星模式的已知限制

* **比采样半径更宽的笔画不可恢复**，因为“背景”样本会落在十字准星自身上。`crosshairneighbourdistance` 正是为此而设的配置项，其可用取值受 ROI 限制：到某个程度样本就会跑到方框之外。
* **十字的中心，即各臂相交处**，其有效方向比臂上更少。在八方向采样下，对角线方向仍能离开十字准星，但若某一点在所有方向上都厚——是一个实心圆点而不是十字——该方法在那里就会失效。
* **不在窗口中心的十字准星**不会被发现，因为监视方框是按窗口矩形定位的。那些为武器瞄准画面而偏移十字准星的游戏需要一项偏移设置。
* **移动或改变大小的窗口**会重新开始累积，因为偏移必须始终指向同一个屏幕像素，统计量才有意义。

## 12. 十字准星模式仍然无法分辨的东西，以及诚实的现状

空间背景让十字准星变得可解，合成测试也能精确地还原出一个。但在真实内容上，它仍然**尚不可信**；这个理由值得精确说出来，因为它不是一个调参问题。

在一切能施加于像素的检验面前，一个十字准星和一笔文字是同一回事：

* 两者都很细，因此两者都与邻域中位数不同；
* 两者都是高对比度的；
* 只要文字没有在滚动，两者在屏幕空间里都是静止的，因此两者在每一帧中都被“覆盖”。

后来加了三道防护，每一道都排除掉问题的一部分，但没有一道是那个正确的检验：

| 防护 | 它排除掉什么 | 它漏掉什么 |
| --- | --- | --- |
| 覆盖率 ≥ 0.85 | 在监视方块中漂移而过的场景结构 | 在屏幕上静止不动的场景结构 |
| 被覆盖像素的多数其 alpha 已被辨别 | 位于静止背景之上的场景结构 | 位于正在运动的东西之上的场景结构 |
| 完全什么都没解出时拒绝输出 | 一个完全静止的场景 | 有一个像素在动的场景 |

在一个文本编辑器上实测（其中不含任何十字准星）：相继几个版本分别产出了 193x193 和 193x94 的“十字准星”，而在被实测的那次运行中，最终否掉它们的是上面第三道防护。结果取决于屏幕上正在发生什么，而这恰恰是一个不可靠检测器所具备的性质。

**正确的检验是运动**，也正是人不用思考就会用的那一个：十字准星是画面中*不*动的那个部分，而其余部分在动。文字随场景一起动，因为它*就是*场景。在监视方块上估计一个粗略的局部运动场，只保留那些运动与邻域不一致的像素，这将取代上面三道防护，而不是加入它们之中。

在这一检验存在之前，十字准星模式应当被理解为一个在固定覆盖层上求解器的可用演示，而不是一件可靠的工具；`ROADMAP.zh-CN.md` 中也是这样列出它的。能让这个问题消失的替代方案是 Windows.Graphics.Capture 后端，它直接提供背景，完全不需要任何推断。

## 13. 观察视图：三格面板、一个网格，以及三个坐标系

重建是一个**过程**而非一个结果，而过程是很难在缺陷报告里争辩清楚的。观察视图就是为了让这个过程可见：三格面板，每捕获一帧就刷新一次，外加一段可以暂停、单步与回放的录制。

| 面板 | 展示什么 | 所在空间 |
| --- | --- | --- |
| 合成图 | 捕获到的区域原样，含光标 | 屏幕 |
| 背景估计 | 模型对同样这些像素的当前估计；尚无样本处接近黑色 | 屏幕 |
| 模型 | 逐像素分类用色相表示，恢复出的 alpha 用亮度表示 | 屏幕，经由指针位置采样 |

### 容易做错的地方

这里有**三个**坐标系同时存在，而且尺寸各不相同：

* **屏幕空间**——捕获区域，光标模式下为 `min(160, 显示器)` 见方，准星模式下为 `CrosshairSize`（默认 256）。
* **背景模型的空间**——同样是屏幕坐标，但它是**迄今为止观察过的所有区域的并集**，所以会随指针移动而增长。一次实测中，256 px 的区域产生了 512×512 的累积区。
* **光标局部偏移空间**——`KindMap` 与恢复出的光标在这里，锚点是指针 hotspot 而非屏幕，范围受 `MaxOffsetRadius` 约束（默认 96 时为 193 见方）。

模型在第三个空间里累积，而被观察的像素在第一个空间里。用当前指针位置去采样模型——`偏移 = 像素 − hotspot`——就把三格面板放到了同一个网格上。这正是"回放可以逐帧对比"和"录制大小固定"的原因。代价是：模型面板展示的是模型对**指针脚下**那些像素的意见，而不是整块累积出的字形。这是**有意的取舍**而非疏忽：若展示整块字形，就得随字形范围增长而重新缩放，于是同一个特征会在帧与帧之间于面板上移动，两帧也就无法用肉眼对比了。

### 怎么读这块面板

| 色相 | 分类 |
| --- | --- |
| 绿 | alpha 由背景变化解出 |
| 青 | XOR 合成，用精确 XOR 掩码写出 |
| 橙 | 因背景在其下方从未变化而被假定为不透明 |
| 红 | 未解出：配对太少，或背景方差不足 |
| 灰 | 从未作为前景出现：光标在该偏移处不覆盖 |

亮度是恢复出的 alpha，并设了下限，使近乎透明的边缘仍能作为边缘可见。所以绿色区域不是单纯"出现"，而是随 alpha 与背景分离而**变亮**——这就是"逐步差分补全"的样子。看开头几帧时面板大部分是橙与红；绿色是在场景于指针下方移动的过程中到来的。

### 是验证过的，不是声称的

`rattrap selftest` 会检查：模型覆盖范围只增不减、已记录配对在无场景变化时不会减少，以及最要紧的一条——**刷新视图不会改变模型**。最后这条防的是一个真实的隐患：背景模型暴露的 `Observe` 会在推进自身样本窗口的同时返回一个估计值，而一个图省事用了它的显示层，就会把画面**写进**它本该只是报告的那个模型里，从而以屏幕重绘的任意频率改变它正在绘制的结果。因此读取是一个独立的入口，而测试断言这种分离确实成立。
